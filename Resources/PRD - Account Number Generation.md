## **Overview **

### Release Notes

- Introduce **Account Number**, a human-readable supplementary identifier displayed alongside Account ID / Account Name on both operator and client platforms UI and API.
- Account Number is structured for readability and includes a check digit to detect manual input errors.

---

### Problem Statement

- The current Account ID is a long alphanumeric string that is difficult for clients to read, remember, and communicate. This creates friction when clients reference their accounts — e.g. confirming a transfer destination or contacting support.
- A **random** number format was chosen after benchmarking with banks and other industries — random numbers are harder to guess than sequential ones, so it is more secure.

---

### Solution Overview

**Account Number format:** `A-NNNN-NNNN-NNNN-C`

- `A` — fixed prefix, same for all accounts
- `NNNN-NNNN-NNNN` — 12 random numeric digits generated by the system
- `C` — 1 check digit (numeric)
- Example: `A-2345-6789-0123-9`  

**Account Generation:**

- New accounts — account number is generated automatically at account creation. The backend verifies uniqueness against all existing account numbers before responding; a collision triggers regeneration.  

**Display & Usage:**

- API call to BE is still using Account ID, API response should include account number also, so FE can show it in the client and operator platform as additional reference.   
\*Service User is using API, so when do the API call, they should use Account ID. same they should be able to see the account number in the response, 
- Account Number is displayed alongside Account ID / Account Name on both operator UI or Client UI.
- Full account number validation, including prefix and check digit is needed when there is processing an action, except filters because we allow the partial search. 
- The backend stores Account Number without separators. The frontend renders it with dashes (`A-NNNN-NNNN-NNNN-C`) for readability.
- Account Number is immutable after assignment (cannot be changed), consistent with Account ID.


**Existing Account (Before the Release): **

- **Existing V2 accounts**  
Account Number are backfilled for all accounts created before this feature is released. Account creation is blocked during the backfill window.  
- **V1 migration rule (future):**
    - V1 uses account numbers in the format `A-XXXX`.
    - When a V1 account is migrated to V2, the account number becomes `A-XXXX-0000-0000-C`:
        - First 4 digits are preserved from the V1 account number.
        - Remaining 8 digits are zero-padded.
        - Check digit `C` is calculated over the full 12-digit base.
        - Example: `A-1234-0000-0000-6`
    - This preserves recognisability for clients who already know their V1 account number.

---

### **In Scope**

- API call to BE is still using Account ID, API response should have the account number, so FE can show it in the client and operator platform as additional reference.

- **Operator Users** — view Account Number on the operator platform; use them for client support.

## **Functional Requirement **

This feature introduces Account Number as a human-readable identifier assigned to every account. The requirements cover three areas: generating and displaying the account number at account creation, filtering accounts by account number, and backfilling account number for accounts that existed before this feature was released.  

### **FR-1: Generate and Display Account Number**

**Requirement Details**  
As the System, I want to generate a unique Account Number when a new account is created and display it alongside Account ID / Account Name across all operator platform and client platform API and UI (service user also should be able to see this) so that every account has a human-readable identifier from the moment it exists.

- API call to BE is still using Account ID, API response should include account number also, so FE can show it in the client and operator platform as additional reference. 
- Service User is using API, so when do the API call, they should use Account ID. same they should be able to see the account number in the response

Account Number format:

\[Prefix\] - \[Base Digit\] - \[Check Digit\] → `A-NNNN-NNNN-NNNN-C`

- `A` — fixed prefix, same for all accounts
- `NNNN-NNNN-NNNN` — 12 random numeric digits generated by the system
- `C` — 1 check digit (numeric)
- Example: `A-2345-6789-0123-9`

**Actor:** System (triggered at account creation)

**Precondition:** A new account is being created.

**Main Flow:**

1. System generates a 12-digit random numeric base.
2. System validates (see Validations).
3. System calculates / generates the check digit.
4. System stores the Account Number on the account table.
5. System returns the account table. Frontend renders Account Number as `A-NNNN-NNNN-NNNN-C`.  

**Validations:**

| **Check** | **Failure** |
| --- | --- |
| Generated 12-digit base does not duplicate any existing Account Number | Discard and regenerate; repeat until a unique base is found. The check digit is calculated from the base using a formula / system that decided by BE, so if the base is unique, the full number is guaranteed to be unique too. |

**Alternate Flows:**

- For existing V2 account (before this epic release), Account pending backfill (no number assigned): System returns **null** as the Account Number value; frontend renders `N/A` in all Account Number display locations.

**Design Constraints:**

- Account Number is stored without dashes in BE. Separator formatting is rendered by the FE.
- Account Number is immutable after assignment; no update operation is permitted.
- Account Number is displayed on both operator platform and client platforms, on every UI and API (service user should be able to see this too) where Account ID / Account Name currently appears, including list views, detail views, filters, etc.
- Any operation that uses Account Number as an identifier must validate the full format `A-NNNN-NNNN-NNNN-C`, including the `A` prefix and check digit. This does not apply to filter/search, which supports partial input.
- The display will follow the new standard convention   

### **FR-2: Filter by Account**

**Requirement Details**

As an Operator User or Client User, I want to search for an account using Account Number (Partial Search), Account ID (Exact Search), or Account Name (Partial Search).  

**Actor:** Operator User, Client User

**Precondition:** The user is on a page that supports account filter

**Main Flow:**

1. User enters Account Number (Partial Search), Account ID (Exact Search), or Account Name (Partial Search). 
2. System validates (see Validations).
3. System performs a matching with all accounts the user has access to.
4. System returns matching accounts.

**Validations:**

| **Check** | **Failure** |
| --- | --- |
| Partial or Exact Search not Valid | No Data |

**Design Constraints:**

- Account Number filter should be available in the page that currently show the Account filter
- The filter should allow dash → following what FE is showing 
- Account Filter should follow the new standard filter convention 
    - Account Page → Account ID, Account Name and Account Number can be filtered separately
    - Other Page → Account ID, Account Name and Account Number can be filtered on the combined filter
- Filter Type
    - Account Name → Partial Search (min 3 character - dash counted as character) 
    - Account Number → Partial Search (min 3 character - dash is not counted as character)
    - Account ID → Exact Search

Note:

- We are allowing the search with dash and without dash
- If the user type less than the minimum character, there is no result shown and a message to input more character will be shown   

### **FR-3: Backfill Account Number for Existing Accounts**

**Requirement Details**

As the System, I want to assign Account Number to all existing V2 accounts that were created before this feature release so that every account has an Account Number after the backfill completes.  
(Should be done after the release) 

**Actor:** System (batch backfill process)

**Precondition:** The backfill process has been initiated. Account creation is blocked for the duration of the backfill window to prevent new unassigned accounts from being introduced mid-process.

**Main Flow:**

1. System identifies all accounts without an Account Number.
2. For each such account, System generates a unique Account Number following the same generation and uniqueness-check rules as FR-1.
3. System assigns the Account Number to the account table.
4. System repeats until all accounts have an Account Number.

- **Check Digit Formula **  
This is what I found during the research. If dev found a better idea, we should follow dev. 

  Check digit calculation (Luhn Algorithm):  
The check digit allows the system to detect if a user typed an Account Number incorrectly. 
    1. Assign weights to the 12 base digits from right to left: odd positions ×2, even positions ×1.
    2. Multiply each digit by its weight.
    3. Subtract 9 from any result greater than 9.
    4. Sum all results.
    5. Check digit = `(10 − (sum mod 10)) mod 10`.

**Example** — base digits `2 3 4 5 6 7 8 9 0 1 2 3` (from `A-2345-6789-0123-?`):

| **No. Position (right→left)** | **Digit** | **Weight** | **Result** | **Adjusted** |
| --- | --- | --- | --- | --- |
| 1 | 3 | ×2 | 6 | 6 |
| 2 | 2 | ×1 | 2 | 2 |
| 3 | 1 | ×2 | 2 | 2 |
| 4 | 0 | ×1 | 0 | 0 |
| 5 | 9 | ×2 | 18 | 9 |
| 6 | 8 | ×1 | 8 | 8 |
| 7 | 7 | ×2 | 14 | 5 |
| 8 | 6 | ×1 | 6 | 6 |
| 9 | 5 | ×2 | 10 | 1 |
| 10 | 4 | ×1 | 4 | 4 |
| 11 | 3 | ×2 | 6 | 6 |
| 12 | 2 | ×1 | 2 | 2 |

- Sum = 51. 
- Check digit = `(10 − (51 mod 10)) mod 10` = `(10 − 1) mod 10` = **9**. 
- Result: Account Number →  `A-2345-6789-0123-9`.
